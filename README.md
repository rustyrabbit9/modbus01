# modbus01

STM32H750XBH6 firmware generated by STM32CubeMX. The project uses CMake,
Arm GNU Toolchain from STM32CubeCLT and a SEGGER J-Link probe.

## CLion

1. Install the **Embedded Development Support** and **STM32CubeMX** bundled
   plugins, then open this repository as a CMake project.
2. In **Settings | Build, Execution, Deployment | Toolchains**, select the
   STM32CubeCLT toolchain. On this machine it is installed at
   `C:\ST\STM32CubeCLT_1.22.0`.
3. Enable the `Debug` CMake preset. Build the `modbus01` target to produce
   `build/Debug/modbus01.elf`, `.hex` and `.bin`.
4. Connect J-Link to SWDIO, SWCLK, GND and NRST, power the target, then build
   the `probe` target. It should identify the STM32H750 Cortex-M7 core.
5. Build the `flash` target. It compiles, downloads, verifies and resets the
   MCU in one action. Do not use the normal desktop **Run** action on the ELF;
   use `flash`, or use **Debug** with CLion's SEGGER J-Link debug profile.

For source-level debugging, add a **SEGGER J-Link** debug profile in CLion and
set the GDB server to `JLinkGDBServerCL.exe`, device to `STM32H750XB`, interface
to `SWD`, speed to `8000`, GDB port to `2331`, and GDB to the STM32CubeCLT
`arm-none-eabi-gdb.exe`. Do not use port `4444` on this machine: Windows has
reserved the complete `4400-4499` range, so no process can listen on that port.

The build automatically finds the newest `C:\ST\STM32CubeCLT_*` installation.
For a non-default installation, set `STM32_CUBE_CLT_PATH` in the CMake profile,
or pass `-DSTM32_CUBE_CLT_PATH=<path>`.

## Command line

With STM32CubeCLT tools available in `PATH`:

```powershell
cmake --preset Debug
cmake --build --preset Debug
cmake --build build/Debug --target probe
cmake --build build/Debug --target flash
```

The default J-Link interface is SWD at 4 MHz. `LoadFile` performs programming
and verification, followed by a second binary verification and target reset.

## Modbus RTU slave

USART2 is a plain Modbus RTU slave at 9600 baud, 8N1, with RS485 DE driven by
GPIO. It answers slave address `1`, function code `0x03` (read holding
registers), up to six registers per request:

| Register          | Value                                   |
| ----------------- | --------------------------------------- |
| `0x0000`          | temperature, 0.1 C units                |
| `0x0001`          | current, mA                             |
| `0x0002`          | voltage, 0.01 V units                   |
| `0x4002`-`0x4007` | year, month, day, hour, minute, second  |

The values are simulated constants: 25.0 C, 1.500 A, 24.00 V and
2021-06-20 13:25:42. Anything else gets a standard Modbus exception response.

A response is `5 + 2N` bytes for `N` registers, so single-register reads fit in
one eight-byte CAN frame but the six-register datetime read does not. Its
17-byte response is split across three CAN frames, which the receiver has to
reassemble.

## CS-CANET100 converter

Configure the converter for bidirectional `transparent conversion`, standard
frame, and a serial-frame character gap of `10`. The UART carries plain Modbus
RTU frames in both directions; the CAN ID of replies is whatever the converter
is configured to send with, not something the firmware sets.

Do not use `transparent conversion with identifier`. It takes the first two
serial bytes as the CAN ID, so every reply would lose its slave address and
function code and arrive as ID `0x103`.
